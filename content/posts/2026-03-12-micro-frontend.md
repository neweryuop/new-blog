微前端被讲得太久，久到它听起来像一种默认正确答案。但拆分本身不是目的，它只是把问题从一处搬到另一处。

## 先看成本

一个单体前端变大之后，你付出的主要代价是：

- **构建变慢**：一个包越来越大，CI 时间线性上升
- **发布耦合**：改一行文案也要整包重新发布
- **协作摩擦**：几十个人在一个仓库里改同一个路由表

微前端解决的正是这三件事。但如果你的团队只有三五个人，包也不大，那么引入微前端只会凭空多出：

1. 多个应用之间的**样式隔离**
2. **共享依赖**的版本对齐
3. 主应用与子应用的**通信契约**
4. 更复杂的本地开发与调试环境

## 一个判断标准

如果下面这句话你答不上来，就别拆：

> 拆完之后，哪个团队可以独立发布、独立回滚？

能回答，说明拆分的收益是真实可度量的；答不上来，说明你只是被“大”这个字吓到了。

## 代码示例

一个最小的 qiankun 注册：

```
js
import { registerMicroApps, start } from 'qiankun';

registerMicroApps([
  {
    name: 'blog',
    entry: '//localhost:8081',
    container: '#sub-app',
    activeRule: '/blog'
  }
]);

start();
```

代码本身很短。长的是它背后那一整套约定。

> 架构是给问题让路的，不是给名词让路的。
